# Сравнение haier_evo_2 и форка AGrigorii/haier_evo, проход 2

**Дата:** 2026-11-11
**Наша сторона:** `origin/main` [`7d9d586`](https://github.com/temandroid/haier_evo_2/commit/7d9d5864be87dd1a8e4e84cd6ff5ec8cd1c00519), релиз [v0.5.0](https://github.com/temandroid/haier_evo_2/releases/tag/v0.5.0).

поверх них ревью №6 (CR-T-070…076). Поэтому сравнивается `main`, а не `dev`, как предполагалось в задаче.
**Форк:** [AGrigorii/haier_evo](https://github.com/AGrigorii/haier_evo) `main` `541574b` (v1.7.1, 2026-11-09).
Это тот же коммит, что в первом проходе ([`agrigorii-fork-review.md`](agrigorii-fork-review.md)):
в `main` форка новых коммитов нет. Есть одна новая ветка, `to-upstream` (`d58e901`, 2026-11-11). В ней

готовит перенос форка в апстрим. Кода в ветке нет.
**Как сравнивали:** статическое чтение кода обоих репозиториев. Код форка не запускался.
Образец формы — issue [and7ey/haier_evo#111](https://github.com/and7ey/haier_evo/issues/111). Строки
вида `api.py:531` у форка относятся к `541574b`, у нас — к `7d9d586`.

## Вердикт

**Прошлый вердикт сохраняется: база остаётся наша, у форка берём идеи.** За день разрыв в нашу пользу
вырос. Из десяти идей первого прохода сделаны шесть (CR-T-057…062), заодно закрыты ещё 14 находок
ревью №5 и №6, которых у форка нет. По архитектуре, практикам HA и устойчивости к сбоям облака мы
теперь впереди или вровень почти везде.

У форка остаётся лучше:
1. **процесс** — SECURITY.md, Issues, пины actions по SHA, mypy, матрица версий HA;
2. **безопасность пароля** — у него пароль не хранится;
3. **устройства** — бойлеры и стиралки;
4. **поведение команд в UI** — ошибка облака видна в интерфейсе, у нас она уходит только в журнал;
5. **несколько точечных приёмов**: честная недоступность после старта из кэша, ограниченное время
   подключения WebSocket, повтор TCP-подключения, более жёсткая чистка диагностики.

Всё это переносится к нам за 1,5–2 дня, переход на его базу по-прежнему не нужен.

## 2. Авторизация и обновление токенов

| | haier_evo_2 | AGrigorii |
|---|---|---|
| Где | `client.py:82-332` (отдельный класс, aiohttp) | `api.py:404-567` (внутри хаба, `requests`) |
| Хранение токенов | `Store(private=True)`, `__init__.py:49-51` | `Store(private=True, atomic_writes=True)`, `__init__.py:71-73` |
| Пароль | хранится в `entry.data` (`__init__.py:116`) | не хранится: удаляется после первого удачного старта (`__init__.py:307-312`), мастер кладёт в запись только токены (`config_flow.py:50-60`, `110-114`) |
| Refresh отвергнут | вход по паролю (`client.py:318-331`) | вход по паролю, если он есть, иначе `ReauthRequired` → reauth (`api.py:483-519`) |
| 401 на данных | refresh → 401 → пауза 3 с → вход → 401 → `HaierConnectionError`, то есть повтор setup, а не reauth (`client.py:336-382`, CR-T-050) | `token_rejected()` и `TOKEN_FRESH` 30 с только для статуса устройства (`api.py:553-594`). **На списке устройств 401 проглатывается** (`api.py:549-551`, `return {}`) — замечание A-2 первого прохода по-прежнему открыто |
| Неверный пароль | только по ответу sign-in, «липкий» `_auth_failed` (`client.py:274-291`, CR-T-042/051) | `AuthUserError` → `disconnect_requested = True` (`api.py:447-449`) |
| 429 | пауза по `Retry-After` с удвоением до 15 мин (`client.py:284-288`) | свои `ResettableLimits` + `add_period` (`api.py:195-209`, `440-442`); ждёт в потоке executor |

**Кто лучше.**
- **Цепочка отказов** — у нас. 401 на любом запросе доходит до refresh и входа, а вердикт «пароль
  неверный» выносит только эндпоинт входа. У форка временный 401 на списке устройств превращается в
  пустой список (`InvalidDevicesList`) и цикл `NotReady`, пока токен не истечёт по часам. Спасти может
  только закрытие WS с кодом 1007.
- **Пароль** — у форка, по безопасности. Для нас это компромисс: без пароля сценарий 2026-11-04
  (refresh отвергнут → 401) кончился бы настоящим reauth, а не самовосстановлением.
- **`atomic_writes` для токенов** — у форка: обрыв питания посреди записи не оставит битый файл. У
  нас `atomic_writes` есть только у кэша (`__init__.py:61-63`), у токенов его нет. Правка в одну строку.

**Перенести:** `atomic_writes=True` в `token_store` (5 мин). Отказ от пароля — по решению владельца.
Вариант-компромисс: хранить пароль, но давать опцию «не хранить» (2–3 ч).

## 3. HTTP, WebSocket и переподключение

| | haier_evo_2 | AGrigorii |
|---|---|---|
| Транспорт | общая сессия HA, `ws_connect(heartbeat=30)` (`api.py:483-488`) | `requests.Session` + `urllib3.Retry` (`api.py:276-302`), `websocket-client` в своём потоке |
| Повторы TCP | нет: один запрос, `ClientTimeout(total=15)` (`client.py:223`, `353`) | connect ×3 для всех методов, read ×2 только для GET, connect-таймаут 5 с (`const.py` `API_CONNECT_*`) |
| Таймаут подключения WS | **явного нет**: работает умолчание aiohttp (`sock_connect` 30 с, `total` 300 с), у сессии HA своего таймаута нет | 10 с на TCP + TLS + upgrade (`api.py:771-782`, `WS_CONNECT_TIMEOUT`) |
| Мёртвое соединение | heartbeat 30 с + ACK-сторож 10 с → новое соединение (`api.py:661-694`) | ping 15/10 с + ACK 6 с → новое соединение (`api.py:1076-1124`) |
| Молчащая сессия | 60 с × 2ⁿ до 8×, вторая подряд — со свежим токеном (`api.py:500-517`) | то же (`api.py:846-880`) |
| Закрытие 1007 | → `invalidate_access_token` (`api.py:549-553`) | то же, плюс слово `token` в тексте закрытия (`api.py:911`) |
| Backoff | 2…60 с, сброс после 60 с жизни (`api.py:436-469`); команда будит цикл раньше (`_wakeup`) | `connect_limits` раз в 5 с (`api.py:195`, `997`), без экспоненты |
| Ресинк после обрыва | > 30 с → REST по всем (`api.py:528-529`) | то же (`api.py:836-839`, отдельный поток) |

**Кто лучше.**
- **Цикл переподключения** — у нас: одна асинхронная задача, экспоненциальная пауза, лог без шума.
  У форка — поток, `threading.Timer` на каждую проверку, и `Event`, `Semaphore` и `Lock` нужно держать
  согласованными вручную. Комментарии `api.py:936-984` показывают, сколько регрессий это уже стоило:
  зависание HA на 3 с при выгрузке до 1.6.4, оставленный сокет до 1.6.1.
- **Ограниченное подключение** — у форка. Если TLS или upgrade зависнут, наш `ws_connect` будет ждать
  до 5 мин, и всё это время команды получают `command_failed` через 15 с. В #111 это пункт 1.7, где
  нам дали 0,25 из 0,5, и оценка справедливая.
- **Повтор TCP-подключения** — у форка. По его наблюдению часть подключений к `iot-platform` не
  получает SYN-ACK. У нас такой сбой означает неудачный setup (переходим на кэш), пропущенный ресинк
  или 401-цепочку, которую нужно начинать заново.

**Перенести:**
- `ws_connect(..., timeout=ClientWSTimeout(...))` и `asyncio.timeout(10)` вокруг подключения (30 мин);
- один повтор GET при `ClientConnectorError` с паузой 0,5 с в `client.async_get` (1 ч).

POST на вход не повторять: у форка connect-повтор POST безопасен только потому, что запрос не ушёл.

## 5. Обработка ошибок и поведение команд

| | haier_evo_2 | AGrigorii |
|---|---|---|
| Иерархия ошибок | `HaierError` → `Auth/Token/RateLimit/Connection/Api` (`client.py:28-66`) | наследники `requests.HTTPError` + `HomeAssistantError` (`api.py:32-66`) |
| Облако запрещает команду (`modifiers`) | `HaierCommandLocked` до отправки, с причиной `off/mode/alarm` и whitelist значений (`api.py:1267-1343`) | то же, плюс подпись причины из экранов приложения (`api.py:1303-1343`), и аварии обслуживания (`filterCleaningAlarm`) не блокируют (`MAINTENANCE_ALARMS`) |
| Вызов сервиса | возвращается после `send_str`; ACK, повтор и ресинк — в фоне (`api.py:661-694`) | **ждёт `command_response`**, `errNo ≠ 0` → `HaierCommandRejected` в UI (`api.py:1103-1117`) |
| `errNo ≠ 0` | REST-сверка, `warning` в журнал, состояние откатывается (`api.py:635-659`) | REST-сверка, затем исключение пользователю (`api.py:1105-1117`) |
| Команда не подтверждена дважды | `lost_commands += 1`, `error` в журнал, ресинк (`api.py:685-694`) | `error` в журнал, ресинк в потоке (`api.py:1131-1135`) |

**Кто лучше.**
- **Сам механизм** — у нас: асинхронный сторож дешевле потока, параллельные команды не мешают друг
  другу (`sent_ws is self._ws`, `api.py:676`).
- **Обратная связь пользователю** — у форка. У нас «облако отказало» (например, `errNo=22` на
  включение блока, у которого авария) видно только в журнале и по откату ползунка через секунду-две.
  У форка в интерфейсе появляется ошибка с текстом. Практика HA — сервис, который не выполнился,
  поднимает `HomeAssistantError`.
- **Аварии обслуживания** — у форка правильнее. У нас любая авария из `trigger.alarms` блокирует
  атрибут (`api.py:1310-1311`). Если облако внесёт `filterCleaningAlarm` в правила, пульт и HA
  разойдутся: из приложения можно, из HA нельзя. На наших AS25PHP3HRA и AS70S2SF2FA такого правила
  не видели, поэтому риск низкий.

**Перенести:**
- в `async_send` ждать ACK асинхронно (`asyncio.Event` на trace, 10 с), при `errNo ≠ 0` и
  непройденной REST-сверке поднимать `HaierCommandError(command_rejected)`. Повтор при молчании
  остаётся фоновым, чтобы сервис не висел 20 с (3–4 ч с тестами);
- исключение `filterCleaningAlarm` из блокировок (30 мин).

## 6. Старт, кэш и доступность

| | haier_evo_2 | AGrigorii |
|---|---|---|
| Порядок | **сначала облако**, кэш — только если облако не ответило (`__init__.py:125-140`) | **всегда сначала кэш**, если он есть, облако — в фоне (`__init__.py:262-272`, `323-328`) |
| После старта из кэша | опрос облака 5…300 с, затем перезагрузка записи (`api.py:359-386`) | `refresh_devices` до полного успеха, перезагрузка только если описание изменилось (`__init__.py:95-159`) |
| Доступность из кэша | `_online=True` (`api.py:768`), `cloud_available` = True ещё 180 с (`api.py:185`, `213-218`): **до 3 мин показываются старые значения как настоящие** | `synced=False` → `unavailable`, пока не прочитано настоящее состояние (`api.py:661`, `1196-1201`) |
| `OFFLINE` от облака | делает устройство недоступным (`api.py:799-808`) | не учитывается: «ONLINE/OFFLINE мигает», вынесено в отдельный датчик связи (`api.py:1197-1201`) |
| Полное перечитывание | раз в 15 мин статусы (`const.py` `REST_REFRESH_INTERVAL`) | статусы раз в 15 мин и список с описаниями раз в 6 ч, новое устройство → перезагрузка (`__init__.py:330-342`) |

**Кто лучше.**
- **Порядок старта** — у нас. Кэш-сначала у форка даёт быстрый старт, но при каждом старте сущности
  строятся по описанию, которому может быть много часов: прошивка, `modifiers`, новые атрибуты. Потом
  при расхождении следует перезагрузка, то есть два построения вместо одного. Кэш как запасной путь —
  правильный выбор для случая, когда облако работает почти всегда.
- **Доступность после старта из кэша** — у форка. Наши сущности первые 3 мин показывают значения из
  файла как живые. Именно в сценарии 2026-11-04 (облако поднялось позже HA) автоматизация увидит
  «кондиционер включён, 24 °C» по данным часовой давности.
- **`OFFLINE`** — спорно, данных нет. У нас `OFFLINE` честно гасит блок, выдернутый из розетки (шаг 6.4
  плана живых проверок). Форк говорит о «мигании», но в журналах прода у нас такого не видели.
  Оставить как есть и проверить на живом.
- **Обнаружение новых устройств** — у форка: раз в 6 ч сверяет список и сам перезагружается. У нас
  новое устройство появляется только после рестарта или перезагрузки записи (в журнале есть подсказка,
  `api.py:598-599`, но только для «пропавших»).

**Перенести:**
- при старте из кэша `_online = False` у устройств, пока не придёт пуш или REST-статус (1 ч, с тестом);
- раз в N часов сверять список устройств и при новом MAC планировать перезагрузку (2 ч).

**Да, сохраняется, и аргументы стали сильнее.**
1. Шесть его главных преимуществ первого прохода у нас уже есть, местами в более полном виде
   (CR-T-063, 070, 071, 073).
2. Его база по-прежнему потоковая. Перенести наши async-сеть, `runtime_data`, `has_entity_name`,
   reconfigure и CR-T-050/070/071 — это всё те же 4–6 дней переписывания чужого файла на 3000 строк.
3. Ветка `to-upstream` показывает, что автор готовит перенос в and7ey/haier_evo. Если апстрим его
   примет, это станет поводом пересмотреть отношения с апстримом (ребейз наших профилей и фиксов на
   новый апстрим или дальше жить отдельно), но не поводом брать форк базой сейчас.

Что могло бы изменить вердикт: форк переходит на asyncio, а нам становятся нужны бойлеры или
стиралки. Ни того ни другого сейчас нет.
